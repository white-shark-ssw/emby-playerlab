# 海报展示层整体设计方案

_2026-10-06，DEV-poster-grid-smoothness。状态：设计方案已整理；用户已确认“提前准备、有限驻留、滑动阶段轻量呈现”的原则并要求整体设计，尚未授权本轮执行代码重构。以下为建议实现，不能标成已实现、已测试或稳定。_

## 1. 目标与真实基线

目标是首页、库页及后续共享海报页面在目标设备上持续平顺：普通向上/向下拖动、惯性滑动、快速反向时，不因海报进入、图片完成或分页追加出现可见停顿/中途跳动。120Hz对应约8.33ms的显示间隔；平均回调频率不是每帧按时呈现的证明。

采用与已验收轮播图一致的原则：准备昂贵资源，让运动阶段消费准备结果。轮播图少量页面可全部驻留；海报墙数量大，必须使用有限窗口、系统组件复用和有界图片缓存。该设计减少明确的长帧来源，不承诺任何设备条件下绝对零长帧。

- 当前已验收整体产品：OnePlayer0.15.27 / Build294；产品源码ca60a034d68d451bc0f93f5681465398131d54c5。
- 本轮审计main：4ec7b816f1d2efd7069de3e300d12f4e4042889b。首页仍是纵向ScrollView/LazyVStack及横向LazyHStack；库页仍是LazyVGrid；库页快照构建/JSON/写盘仍为同步路径。
- Build283 /39014a03e2681aed3647bdd6d7d7b1c82b8cc4f6的原生库页.items、后台有序持久化、常驻隐藏NavigationLink修正，仍在Draft PR#282；本轮重新确认head一致、未合并。已接受的分页子结论保留，不能声称已经包含在Build294。
- Build283原生单元格仍使用UIHostingController<AnyView>承载V3PosterCard，同ID更新重新配置全部可见host；这些是优化切入点，不是最新抖动根因已被证明。
- 最新用户现象未提供安装Build、日志/视频及时间点。性能归因前需补齐准确基线，但整体方案可以先完成。

## 2. 组件边界与状态所有权

下列名称描述拟新增职责，并非声称源码已有同名API。

| 层 | 职责 | 状态所有者 |
|---|---|---|
| 页面业务模型 | 影片顺序、分页、筛选、排序、收藏、观看状态、成功数据持久化 | 现有Home/Library/Search等模型 |
| 页面适配器 | 将业务数据映射成稳定section/item标识及轻量显示字段，计算受影响项 | 页面展示控制器；不复制业务分页模型 |
| 原生集合视图 | 纵向/横向滚动、复用、布局、预取回调、点击反馈 | UIKit；不另加手动积分或插值滚动 |
| 原生海报单元格 | 图片、文字、年份、进度和角标的固定布局 | 当前绑定的item/request标识；无需每格SwiftUI host |
| 图片请求与准备协调 | 可见需求与预取需求共用请求，后台读取/解码，通知准备完成 | 一套共享请求协调；复用既有磁盘/decoded缓存 |
| 已验收外围 | Home轮播runtime/native surface、Dock位置、系统导航 | 原有所有者继续权威 |

业务模型更新一次，可以产生新增项、删除项或显示字段变化；图片完成不回写整个业务数组，不触发根页面ObservableObject发布。普通滚动也不向整页SwiftUI状态逐帧发布位置。

页面适配器只做展示映射，不新增一个拥有全部影片业务状态的全局“海报模型”。不因建立共享组件重写API、EmbySession或播放生命周期。

## 2A. 所有三列结果页共享完整海报墙，页面通过适配器接入

用户明确要求考虑库页以外的收藏更多、标签筛选、演职人员/角色入口、输入搜索、推荐/更多观看等海报墙。这里的“3×3”是三列并持续纵向滚动的网格，不是固定九张海报上限。

本轮在main dd5ec86f89f777b1fb00514c02dd6c37bc3f17b8核查实际定义与调用。当前已有共享EmbyPosterGrid，但它主要是LazyVGrid片段；外层ScrollView、初始加载、分页回调、卡片样式/加载器及导航仍分散。这证明存在实际共享需求，重构不是为了假定的未来入口。

### 建议抽象的范围

共享核心包含固定布局、原生滚动宿主、cell复用、图片占位/准备/目标项更新、有限首屏资源需求、回顶及普通展示状态。外层页面保留自己的标题、工具栏、筛选、排序、业务模型、API与系统导航；不要把每个页面的私有过滤逻辑搬进一个巨型公共模型。

这是“一套核心 + 两类布局适配”：通用三列网格优先推广；首页使用sectioned横向行适配。核心单元格/图片协调/资源预算共用，首页Hero/native surface继续独立负责。不为每个入口复制一个控制器实现，也不把任意SwiftUI AnyView重新塞回每格以维持旧调用形式。

未来接入合同（职责设计，不是源码已有API）：

- 输入：稳定且包含来源的item身份、已加载的轻量展示字段、图片请求身份/规格、少量明确cell类型、布局参数、业务模型提供的初始/追加/错误状态及hasMore。
- 输出：点击了哪个来源的item、接近已加载尾部、用户主动刷新、回顶动作等事件；页面适配器调用真实模型方法。
- 核心维护滚动/cell/图片需求；模型继续独占分页frontier、isFetching、去重与请求代次。列表接近尾部只是需求信号，不替模型另存一套nextStartIndex。
- 同ID同字段不更新；字段变化只更新真实变化项。新增元数据与图片到达是两种更新，不能都走整个snapshot替换。
- 列表内部没有导航栈或播放控制器。点击回调由既有页面/路由选择详情、剧集对应Series或人物作品等目标，保护系统push/pop与原有单一选择所有者。

用户说的“推荐页面的更多观看”须按实际导航调用定位具体目的页；现已确认推荐网格及多服务器搜索结果的“更多”调用，未声称存在一个猜出的同名API。实施前补完该路由登记；所有经过通用海报墙的实际目的页纳入迁移，不凭称呼重写推荐数据源。

EmbyPosterGrid也被库类别封面/文件夹封面等使用，这些item并非都可直接进入影片详情。它们采用明确原生cell类型和页面点击回调，不通过“所有item都视为影片”兼容它们。细节如人物姓名、影片年份、进度/已观看角标可以是少量内容变体；保留既有已显示字段，不添加新的评分/角色能力。

### 页面身份与生命周期

跨服务器可能有相同item.id，keyword/genre/person/tab变化也可能复用同一视图位置。展示item身份必须结合真实来源，页面身份必须包含来源/用户、入口类别、查询/过滤/排序等实际条件，旧图片/数据回调校验对应代次。不要让不同服务器或不同查询共享选择、首屏准备或分页状态。

图片命中和元数据就绪是不同条件。Library/Favorites有既有持久化快照；人物/过滤/搜索等结果页不能被自动宣称重启后已有同样的元数据快照。所有入口可以复用已缓存图片，但是否恢复结果元数据由既有页面合同决定；新增搜索结果持久化必须另有明确需求，不能为了“共享海报墙”偷偷改变Search生命周期。

详情push/pop继续消费同一页面数据与滚动状态；主动切换筛选/排序或Search离开Dock按既有规则结束对应页面需求。资源需求随其所属页面释放，共享缓存继续可用，不引入一个保存所有历史查询UIView/UIImage的全局页面池。

### 还需纳入的交付条件

1. 确认所有实际调用点和目的路由，逐项登记迁移、验证及待迁移状态，不能只完成Library后宣称“共享重构完成”。
2. 保留真实分页策略，包含Library等60条、搜索结果18条、推荐9/+6及不分页入口。
3. 核对元数据字段/图片规格/内容类型/点击目标，不将人物、文件夹或Episode强行走同一影片路由。
4. 同库往返、详情返回、深处回顶、切换query/tab以及多服务器同ID交叉验证；标题栏、安全区与Dock仍由页面/既有宿主负责。
5. 所有页面图片需求计入同一预算。特别核查现有Search recommendationPosterImages累积pin与共享准备如何衔接，避免共享核心之外继续无限保留图片；Search数据与Dock lifetime不可改变。
6. 构建/真机结果按具体入口记录覆盖范围；公共核心验证不能代替每个入口的分页/点击/回返验证。


## 3. 库页：确定布局、复用单元格、图片独立到达

建议使用原生UICollectionView三列布局，沿用现有左右间距、行间距、2:3海报、名称/年份高度和角标外观。

1. 取得已加载的影片元数据，即可确定卡片位置和高度；背景占位、图片和下载失败状态使用同一几何尺寸。
2. 单元格的UIImageView、UILabel及角标/进度视图创建一次后复用。固定布局不依赖图片原尺寸；标题截断及年份缺省不改变高度。
3. 在出现在屏幕前的准备阶段完成轻量绑定；可见时命中prepared image则直接显示。真正首次下载未就绪时显示海报框+已有影片名并发起同一异步请求；磁盘暖缓存的正常进入以提前准备后直接呈现为验收目标，不能长期接受每次重新闪占位。
4. 图片完成只更新当前item的图片显示。按稳定ID定位，并校验当前图片请求标识和绑定代次，避免复用后的旧回调贴错图片。
5. 图片到达不使用整页reloadData、重新设置全部可见rootView、自适应尺寸或全局隐式动画。
6. 宽度/真实版式变化时才重算布局；图片完成不触发布局失效。正常更新不写contentOffset去“修正”视觉跳动。

“5000部影片”是逻辑数据规模；不需要5000个UIView或5000张解码位图。布局属性可以轻量计算，实际视图由UIKit复用。

首版保留现有60条顺序分页语义：为已加载元数据中的海报提供图片占位和预取，不提前为未知item伪造LibraryItem或可点击条目。现有libraryItems支持StartIndex/Limit及totalRecordCount，但“预建完整5000个空槽、直接滑到未加载的第4000项”还需要按范围加载、缺页和新导航规则，属于另一种数据访问设计，不自动包含在本次重构。

## 4. 首页：共享海报能力，纵向运动保持单一权威

最终建议首页内容使用一个原生纵向集合视图组织section，横向分组采用原生横向滚动section；不继续在每张海报中承载SwiftUI子树。

保留现有section顺序、我的媒体、继续观看、各库最新、“更多”、卡片样式和点击目的地。竖版海报、横版继续观看、媒体库入口可用不同原生cell变体，共用图片准备服务和更新合同。

已验收轮播图继续由原有native surface/runtime负责。内容控制器提供与当前Hero精确相同的顶部占位及交互宿主位置，原生纵向偏移经一个适配入口传给现有HeroScrollState/bridge；不能重新引入整页逐帧重建、第二个轮播进度所有者或重新调节已验收动画。

Home的顶部安全区、Hero footprint、下方共同底色、下拉拉伸/刷新、回顶命令及Dock底部内容避让必须保持。Dock位置继续归ServerDockHost，内容集合视图只使用共享避让值，不自行硬编码86或重新算Dock位置。

推进顺序先做库页，验证共享cell/图片合同，再替换首页内容宿主。首页接入时要实测横向section的提前准备行为；不假设任意内层滚动实现一定完整转发预取回调。

## 5. 图片准备：磁盘有图不等于可直接显示

现有EmbyImageDiskCache是磁盘图片权威，EmbyDecodedImageRenderPool是解码内存权威；保留已有后台ImageIO缩略解码能力。不另建各页面自己的磁盘缓存/无上限UIImage字典，也不重复解码已经prepared的UIImage。

统一流程：

请求当前显示规格 → 查询decoded memory → 后台读disk → 缺失时网络获取 → 后台按显示像素规格解码 → 存既有内存池 → 通知对应item准备完成。

- 预取和可见请求使用同一请求标识及in-flight任务，避免同一图被重复下载、解码。图片tag/规格改变必须产生相应新请求身份；沿用真实API/缓存规则。
- 可见需求优先于近处预取。下载和解码都有有界并发，避免Task.detached数量随影片数增长。
- 控制器只表达哪些item可见/即将需要，服务统一协调。取消一个离屏订阅不能取消仍被其他可见cell需要的共享任务。
- 方向改变或快速掠过时，撤掉无消费者的远处预取、更新优先级。下一屏没准备好仍显示稳定占位；不阻塞滚动，不等所有图下载完成才能进入页面。
- 图片只替换对应的image view；默认不加每张图的淡入动画、动态模糊或单独旋转loading动画。
- 网络结果若已可用于解码，不应强制等待磁盘写入完成才让可见图片显示；写盘顺序、异常处理及与现有缓存actor的并发要在实施时核实，不能新建重试/补偿链。
- 后台解码并不证明首次GPU呈现没有成本；真机仍要看图片adoption、提交与render尾部，必要时优化同帧集中到达，而不靠固定timer或滑动时暂停所有图片掩盖问题。

优先使用UIKit原生数据预取及cell准备机制。预取不是必达回调，可见绑定必须支持同一正常加载路径，不能把“预取曾发生”当成显示的前置条件。

## 6. 准备窗口与内存预算

组件复用队列由UIKit管理，不再建立一个平行的手工UIView对象池。图片准备窗口覆盖可见项及有限邻近项，与分页数据规模分离。

准备需求包括当前位置可见/邻近区，以及独立于当前位置的有限首屏集合（详见6A）。初始A/B可比较“可见区+前后约一屏”的邻近准备范围；这是待测起点，不是EX内部参数或已验证最优值。实现先利用系统预取，只有测到真实预取不足才增加明确的几何邻近窗口，避免同时维护两个预取权威。

全应用各页面共用图片预算：现有decoded pool为64项/96MiB的NSCache配置，首版不凭空扩大。NSCache限制不是整个App内存硬上限；可见image view、准备窗口强引用、轮播资源和解码in-flight都会持有图片，验收必须统计实际峰值。窗口释放远处引用并取消无用准备，不能仅检查NSCache配置就宣称有界。

按实际显示像素准备位图，不把文件压缩大小当成解码内存大小；粗略估算为像素宽×像素高×4，加上实际对象/临时缓冲及渲染开销。具体缓存/并发数通过目标设备数据选择，不在设计阶段猜一个更大的预算。

内存压力时释放可丢弃的远处准备及decoded缓存，磁盘图片和既有页面元数据缓存继续复用；不改Player会话缓存语义。

## 6A. 磁盘命中、首屏准备与深处回顶：本次补充的明确体验合同

用户补充的EX观察：只有首次下载图片时看见占位；磁盘已有图时，重启App、普通往返及从约第2000部影片处点击屏幕顶部快速回顶，体验上都像内容一直已加载。EX是否使用虚拟列表未知，不能由这一体验推断其全部图片常驻内存。

IMG_8037.png的可见占位是固定的灰色圆角海报矩形加已经显示的影片名，部分既有评分信息也可见；不是整张没有元数据的骨架卡片。此图用于确认用户所说的占位语义，不要求新增评分功能、复制影片内容或推断竞品内部性能。

### 占位语义

卡片的元数据与图片独立准备。已知item立即显示现有影片名、已有角标/年份/进度等真实字段；图片区域保留最终海报的同尺寸框。不得为了“loading”把影片名清空、把整卡替换为骨架、改变高度或反复出现刷新动画。

首版的正常体验目标：真正首次网络下载允许这种图片占位；图片磁盘已命中的正常往返/重新进入，应靠提前准备直接显示海报，不把“有磁盘缓存仍每次明显闪灰框”当成合格实现。磁盘命中仍需读取及解码，不能保证任意图在任意瞬间同步零成本显示；实现不得因此改成主线程读盘或等待全部图的阻塞门禁。异常图片失效/内存压力等与正常暖缓存验收分开记录。

### 页面元数据和图片驻留分别管理

已加载影片的顺序、item身份及显示元数据保留在现有页面业务/快照所有者中；不能因为图片离开准备窗口就删除元数据、缩短列表或重置分页起点。页面可以保存大量轻量元数据，但解码图片及真实控件保持有界。

这允许在已加载到第2000项后回顶：原列表仍在，只是系统切换复用哪些cell。虚拟化与“回顶没有重新加载断点”兼容。数据分页、控件复用、图片内存淘汰是三个独立生命周期。

### 首屏是已知的远距离目标

仅有“当前位置前后预取”无法覆盖从第2000项突然回到顶部。因此在同一个图片准备协调器内增加当前页面的首屏准备需求；它是一个固定大小的资源需求集合，不是第二个缓存或第二个滚动所有者。

- 首屏首次准备完成后，其已准备UIImage保留有限强引用，在该页面正常前台浏览期间不随远处滚动被淘汰。图片仍来自原decoded pool；不复制位图或另建disk目录。
- 首屏集合按真实viewport/layout确定，包含顶部立刻可见卡片和必要小缓冲，不按整库数量增长。
- 优先级：当前可见需求、回顶目标首屏、邻近预取；远处预取可以释放。首屏已准备时不再提交重复读取/解码任务。
- 统计共享cache、当前可见、首屏引用及in-flight合计的真实图片驻留。多个页面不能各自无上限钉住首屏；只保留当前浏览及明确需要即时返回的页面需求，并服从全局预算。
- 排序、刷新、页面/用户/路由身份或真实版式变化时更新首屏item/request集合，旧代次结果不贴到新首屏。
- 正常深处回顶直接使用既有元数据和prepared首屏图片，不refresh页面、重走第一页API、整页reloadData、清空再填充或等待磁盘任务完成后才开始回顶。
- 点击状态栏的系统回顶与产品回顶命令接入同一页面/滚动所有者；保持当下用户要求的快速回顶体验。首屏准备是资源合同，不另加手动滚动插值或定时器。
- 首屏缺少缓存且首次下载尚未完成时保留图片框+影片名；不能承诺尚未获取的真实图片已经可见。

### App关闭后的重新进入

App关闭后内存强引用消失，磁盘图片和现有页面元数据快照仍保留。重新进入时优先恢复对应页面的已缓存元数据，并优先为首屏完成后台磁盘读取和显示尺寸解码；附近图片随后准备。能在现有导航/启动恢复中提前表达需求时提前表达，但不启动全库图片读取，不改变Search已冻结启动或页面生命周期。

正常磁盘命中不重新下载，不显示整页loading后再重建内容。冷进程的首次首屏呈现必须作为单独验收场景：如果明显重现灰框/重载断点，不能用“磁盘本来就是异步”解释为已完成，需通过真实准备时机和耗时继续改进。方案不把保存全部解码位图到磁盘当成新的格式或缓存权威。

### 首页采用同一合同

首页海报行采用相同的元数据保留、图片占位、磁盘暖缓存及首屏准备合同。固定数量且经预算核实的首页图片可以比大库更充分地准备，但不自动新增全库或无上限驻留。首页回顶所需资源包含顶部海报section及已经由既有轮播所有者准备的Hero；不复制轮播资源或修改其runtime。


## 7. 内容更新与持久化

| 事件 | 允许的操作 | 不应发生的连带工作 |
|---|---|---|
| 普通滑动 | UIKit滚动及轻量可见/预取需求变动 | 根页逐帧发布、全列表diff、磁盘读写/解码在主线程 |
| 图片完成 | 按item身份更新单张图片 | 全页reload、全部可见cell重新配置、尺寸变化 |
| 播放状态/收藏变化 | 更新真实变化项的角标/进度/字段 | 重建未变化海报 |
| 下一页元数据完成 | 追加对应item，保留当前滚动连续性 | 重置旧item或人工回写偏移 |
| 排序/手动刷新 | 按既有语义更新结构，取消过期图片订阅 | 老请求更新新排序位置 |
| 成功数据持久化 | 保持后台有序构建、序列化及原子写入 | 在MainActor处理整个累积数据集 |

Build280/283有序后台Library持久化是有证据支持的修正，实施时从原始变更提取并结合最新Build294逐项集成，不能直接合并历史stack及覆盖新Dock/Home源码。

首版不引入固定延迟、watchdog、滚动插值、decelerationRate调参或“滑动就停止更新”门禁。图片回调若仍形成集中提交长帧，先测实际来源，再使用系统更新事务/按真实帧边界合并受影响ID等最小有证据方案；不要预建第二套display-link调度器。

6. **首页及横向行接入。** 再用sectioned native content承载海报行并接既有轮播、刷新、回顶和Dock合同；独立回归高频桥接与手势。
7. **最终验证与交付。** 分配唯一Build/版本，完成CI/IPA及身份/MinOS核验后真机验收。只在授权实施后执行这些代码阶段，本轮仅规划。

## 9. 验收与诊断

- 冷图：首次可见立即有稳定占位，图片异步到达，布局无跳动。
- 磁盘热/内存冷：后台读取/解码不形成可见集中长帧。
- 内存热：往返滑动验证复用路径，不能重复创建host、解码或下载。
- 数据固定与分页分别测；首次进入、普通拖动、惯性、快速反向、横纵混合、详情返回及下拉刷新分别测。
- 在合法滚动范围内统计真实contentOffset反向、零位移→追赶与画面长帧；端部bounce、用户真实反向及刷新动效单独标识，不能当成中途异常。
- 采集帧间隔p50/p95/p99/max及>=16.7/25/33.3ms事件，与cell prepare/configure/layout、图片decode/adopt、snapshot apply/insert、持久化时间对齐；CADisplayLink回调不是已呈现FPS证明，必要时结合Animation Hitches/提交/渲染证据。
- 以屏幕录制关闭的目标设备结果判断性能；录屏辅助定位画面，不能用30fps录屏证明120fps。
- 长列表与持续往返验证内存峰值、in-flight数及下载量不随访问影片数无限增长；真正首次下载允许海报框+影片名占位，但不允许停住滚动。正常磁盘暖缓存往返不以反复灰框作为完成标准。
- 已缓存库页滚动至约第2000部影片，再点击系统状态栏顶部/产品回顶入口：首屏影片与海报直接出现，无首次页重请求、整页loading、明显占位闪现或主线程读盘长帧。首次缓存已完整建立与内存压力场景分别记录。
- 磁盘暖缓存下关闭并重启App，进入同一库页与首页：先恢复已有元数据并准备首屏，验证不重下海报、不出现明显重载断点；内存暖/磁盘暖/首次网络下载不可混为同一测试。
- 保护Build293轮播切换/接管/共同底色、Build294Dock/键盘、原生push/pop/侧滑返回、页面缓存、Search生命周期及iOS15/P0。
- CI、IPA、真机通过及稳定冻结分别记录。设计完成不等于任何性能改善已发生。
