# 0.5.1 真机日志分析：item 63368

日志时间：2026-08-02，包含连续两次播放。

## 第一次播放

- 上游主下载不是瓶颈。主 Range `3407872-996085873` 在 40.283 秒内完成 992,678,002 字节，日志速度约 24.6 MB/s。
- 21 次 Seek 中，前 19 次首帧恢复低于 100 ms；最后两次分别约 3.02 秒和 3.12 秒。
- 主下载在 12:28:28 已到达文件末尾；约 8 秒后播放器停在 230.436 秒。
- 停滞时 `mainCursor=996085874`、`mainRunning=false`，从播放器实际需求字节处至少已有 32 MB 连续缓存，但等待原因仍是 `AVPlayerWaitingToMinimizeStallsReason`。
- 结论：第一次失败不是 115 下载速度不足，而是 AVPlayer 在 localhost 资源已有数据时仍进入主动防卡顿等待；原恢复逻辑看到缓存充足后直接返回，没有推动 AVPlayer 重新播放。

## 第二次播放

- 初始主下载明显较慢，实时约 6-7 MB/s，平均最终约 6.2 MB/s。
- 9 次 Seek 只有 2 次低于 100 ms；7 次超过 500 ms，4 次超过 1 秒，最长约 3.145 秒。
- 主下载线程被实际 HTTP Range 反复迁移：约 104 MB → 357 MB → 138 MB → 387 MB → 756 MB → 280 MB → 943 MB → 315 MB → 960 MB。
- 这些位置同时包含当前播放需求、旧 Seek 连接、音视频分段和 AVPlayer 的历史大 Range。原算法把它们全部视为主下载锚点，导致上游连接不断取消和重建。
- 自适应线路探测在主下载和 Seek 下载之外又创建第三条连接，其中一次返回 403；同一时间其他 Range 仍能返回 206，因此这不是整条 115 临时直链真正过期，更像额外并发连接被拒绝或限流。
- 拖动到较远位置后，真正接近目标的 Seek Range 能达到约 7.3-10.0 MB/s，说明“拖动后速度变快”来自重新建立了更合适的 Range 连接，而不是缓存统计错误。

## 0.5.2 对应修复

1. 传输层 AVPlayer 关闭主动防卡顿等待；停滞时先立即播放，再执行轻量软重 Seek。
2. 文件头尾小范围元数据请求不再迁移主下载线程。
3. Seek 紧急通道立即读取目标 16 MB；主下载仅跟随最后稳定 Seek，并从紧急窗口之后继续。
4. 最近 Seek 周围之外的旧 Range 不再进入紧急队列；等待 5 秒仍未命中的旧 localhost 请求会被取消。
5. 实际需求迁移增加 Seek 保护期、距离相关性和迁移冷却。
6. 115 CDN 禁用第三条线路探测连接。
7. localhost HTTP 日志增加随机 `server=` 标识，用于区分已经停止的旧服务与当前播放服务。
