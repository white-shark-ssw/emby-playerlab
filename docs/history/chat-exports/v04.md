### 1. 63368：这次日志说明了什么

先看空洞。0.12.4 的 `strict-two-segment` 只是禁止快 Lane 在当前两段还没共同闭合时继续跑“第三段”，**并没有禁止第二条 Lane 在第一段尚未完成时先下载第二段**。

日志里有一个非常典型的例子：

```text
slot0 = 0 - 4 MiB
slot1 = 4 - 36 MiB
```

到 `18:13:10.296` 时：

```text
frontier = 3 MiB
cached ≈ 35 MiB
slot0 = 0-4 MiB
slot1 已经跑到 36-64 MiB
holes=0
```

实际上这时 **3-4 MiB 仍然没有缓存完成，而 4 MiB 后面已经缓存了一大块**。所以物理状态就是：

```text
0 ───── 3M   4M ───────────────── 36M
██████████   ████████████████████████
          ↑
        1 MiB gap
```

只是当前 `holes=0` 这个诊断口径没有把这种“连续前沿之后的稀疏 gap”算进去。也就是说，**日志里的 holes=0 不能证明缓冲真的没有洞**。`EmbyPlayerLab-1786212947.log`

而现在 UI 又是直接画 `UnifiedTransport` 的真实 `playbackRanges`，每一个稀疏区间都会单独画一个 Capsule，因此这种 gap 会直接显示出来。

这里需要修正我们之前对“双 Lane + 绝对无洞”的预期：

> 只要两条连接同时下载相邻区间，而且第二条比第一条快，**下载过程中暂时出现 gap 是数学上不可避免的**。

如果为了绝对不产生物理 gap，让 Lane B 等 Lane A 完整结束再开始，那基本就退化成单通道，正好与现在最需要解决的速度问题冲突。

所以我下一版不会再为了“看起来绝对无洞”牺牲双连接速度。正确处理应该是：

- **真正永久遗漏的 gap：必须修；**
- **两 Lane 并行时的临时 gap：允许存在；**
- 普通播放器进度条以“当前连续缓存前沿”为主要缓冲显示；
- 稀疏的远端已缓存块可以放到诊断显示，不再让正常 UI 满屏碎片；
- Seek 跳过的区域本身就应该允许留下 sparse hole，否则每次 +10 秒还回头下载已经跳过去的数据，会浪费带宽。

所以这部分不是简单再改一次 wave 算法，而是要把“**连续可播缓存**”和“**稀疏已缓存数据**”重新区分清楚。

```swift
player.automaticallyWaitsToMinimizeStalling = true
```

普通首次播放调用的是：

```swift
player.play()
```

只有 Seek 的 `immediate` 路径才会：

```swift
player.playImmediately(atRate: 1)
```

这意味着 AVPlayer 有权自己判断“虽然已经能显示第一帧，但我再等等，避免马上 Stall”。

以前网络够快的时候，这个等待可能只有几十、几百毫秒，你根本感觉不到；这次它被起始连接的低速明显放大了。

playImmediately(atRate: 1)

### 我建议改变的是“缓冲条语义”

当前 UI 明确把所有真实 sparse byte ranges 都直接画出来，代码注释甚至就是：

> `Sparse seeks remain sparse here: a hole is rendered as a hole`

也就是说现在这个 UI 是一个**底层缓存调试器**，而不是普通播放器意义上的“已缓冲进度条”。

我建议正式播放器改成两层概念：

**主灰色缓冲条：只显示当前播放锚点开始的连续缓存前沿。**

例如底层实际：

`████████ 0-260MB`
`空 260-270MB`
`████████ 270-310MB`

`████████ 0-260MB`

等前面的 Lane 把 260-270 补齐以后，灰条会直接推进到 310MB。

- 不修改现在已经很优秀的双 Lane 调度；
- 不虚报“当前位置可以连续读取”的缓存；
- 不会因为两个并行 Lane 几百毫秒的速度差，在 UI 上不停闪出洞；

## 我建议把它升级成一个正式的「Video Geometry」模块

目前播放器实际上没有真正的“视频画面布局系统”。

现在 `PlayerScreen` 基本就是：

```text
整个屏幕
  ↓
GeometryReader
  ↓
MPVPlayerSurface
  ↓
CAMetalLayer 填满整个 Geometry
```

而 `MPVPlayerSurface` 又直接负责：

- layer bounds
- position
- contentsScale
- drawableSize

这在“只有一个全屏画面”阶段勉强可以。

但后面一旦加入你说的：

- 横屏按钮
- 竖屏按钮
- 自动旋转
- 自适应
- 铺满屏幕
- 可能以后还有拉伸、裁剪、画面比例

继续靠这个 Surface 自己猜尺寸会越来越乱。

### 更合理的是分成三个完全不同的概念

**第一层：屏幕方向 Orientation**

只管：

```text
portrait
landscapeLeft
landscapeRight
auto
```

它决定整个播放器 UI 是 430×932 还是 932×430。

---

**第二层：Video Viewport**

这是播放器真正允许视频显示的矩形。

比如横屏：

```text
┌──────────────────────────────────────┐
│                                      │
│        Video Viewport 932×430        │
│                                      │
└──────────────────────────────────────┘
```

以后即使有：

- 刘海避让
- 字幕区域
- 顶部控制栏
- 底部进度条
- 小窗模式

也都是先算好这个 viewport。

播放器引擎不应该自己去推测 SwiftUI 的 Geometry。

---

**第三层：Content Mode**

然后视频自己决定如何放进 Viewport。

我建议第一版就定义三个标准模式：

| 模式 | 行为 |
|---|---|
| **自适应** | 保持比例，全部视频可见，允许黑边 |
| **铺满** | 保持比例填满屏幕，多余部分裁掉 |
| **拉伸** | 强制填满，不保持宽高比，可作为高级选项 |

AVPlayer 本身就有完全对应的 `resizeAspect / resizeAspectFill / resize`。([Apple Developer](https://developer.apple.com/documentation/avfoundation/avlayervideogravity?language=objc&utm_source=chatgpt.com))

MPV 也有自己的比例、panscan、zoom、pan 等画面控制能力，因此不应该通过缩放 CAMetalLayer 来实现“铺满”；**CAMetalLayer 始终代表 Viewport，视频如何适配应该交给 MPV 的视频渲染参数。** MPV 官方也明确区分了 `panscan`、`video-zoom` 和视频平移等功能。([mpv](https://mpv.io/manual/master/?utm_source=chatgpt.com))

这个分离非常重要。

# 为什么这很可能顺便解决现在的偏移

我现在最想改掉的其实不是某个数字，而是当前这个关系：

```text
MPVPlayerEngine
    ↓
自己创建 CAMetalLayer
    ↓
SwiftUI 创建 UIView
    ↓
再把这个 CAMetalLayer 当 sublayer 挂进去
```

当前源码确实是 `MPVPlayerEngine` 自己持有：

```swift
var displayLayer = MPVMetalLayer()
```

然后 UI 再 attach 它。

这个结构对于旋转比较危险，因为：

**Layer 的生命周期属于 Engine，但尺寸生命周期属于 UIView。**

两边不是同一个对象所有者。

以后我更倾向的结构是：

```text
VideoSurface UIView
     │
     └── 自己的真正 backing CAMetalLayer
               │
               └── MPV / MoltenVK 直接渲染这里
```

也就是说：

**不要 Engine 创建一个孤立 CAMetalLayer，再挂到 UIView。**

而让最终在屏幕上的那个 UIView 本身就拥有真正的渲染 Layer。

这样：

```text
UIKit rotation
    ↓
UIView bounds
    ↓
CAMetalLayer bounds
    ↓
drawable / swapchain
```

生命周期天然是同一条链。

然后 MPV 只是“连接到这个 Surface”，而不是“拥有这个 Surface”。

这比继续在 `layoutSubviews()` 里抢 MoltenVK 的 `drawableSize` 控制权稳健得多。

这一步会涉及 MPV Surface 生命周期，所以到真正实现时，我会建议临时使用**高推理**，而不是像这两版一样快速修一个尺寸判断。
