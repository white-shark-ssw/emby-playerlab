## 当前架构真正的问题

现在播放器实际上有三个“尺寸拥有者”：

```text
PlayerScreen / SwiftUI
        ↓
VideoLayoutCoordinator
        ↓
430×932 / 932×430
        │
        ▼
MPVSurfaceUIView
        ↓
CAMetalLayer frame / bounds
        │
        ▼
MPV gpu-next
Vulkan / MoltenVK
        ↓
真正 drawable / swapchain
```

前两层现在其实是工作的。

`VideoLayoutCoordinator` 算出了正确尺寸，`UIView` 的 bounds 正确，`CAMetalLayer` 的逻辑 frame 也正确。

**真正断开的地方是：**

> `CAMetalLayer.frame 已改变` ≠ `MoltenVK 的 Vulkan swapchain 已按这个尺寸重新建立`

当前 #98 为了避免上次崩溃，又形成了这样的状态：

```text
UIKit：
我只改 frame / bounds / scale

MoltenVK：
drawableSize 归我管理

两者之间：
没有可靠的“viewport 已改变，请重建 renderer”的握手机制
```

所以 `setNeedsDisplay()` 并不能保证 Vulkan swapchain 完成 resize。

而我们上轮尝试：

```swift
layer.delegate = hostView
```

又已经被真机证明会导致进程退出，所以这条路也不能再走。当前热修确实专门撤掉了这个 delegate 接管。

## 我认为之前最值得重新审视的一点：我们可能不该把 MPV 的 CAMetalLayer 单独“抽出来挂载”

我重新对照了 **MPVKit 1.0.0 自己的 iOS Demo**。

官方 Demo 的 SwiftUI 接入不是：

```text
拿到 CAMetalLayer
↓
塞进另一个 UIViewRepresentable
↓
外部管理 frame
```

而是直接：

```swift
UIViewControllerRepresentable
    ↓
MPVMetalViewController
```

也就是让整个 MPV Metal ViewController 自己作为播放器渲染宿主。

而这个 `MPVMetalViewController` 自己：

```text
拥有 MetalLayer
↓
把 MetalLayer 加到自己的 view.layer
↓
在 viewDidLayoutSubviews 更新 metalLayer.frame
↓
同一个 Controller 同时拥有 mpv + MetalLayer 生命周期
```

MPV 的 `wid` 也是直接绑定它自己持有的 `metalLayer`。

MPVKit 甚至自己提供了一个定制 `MetalLayer`，专门规避 MoltenVK 修改 `drawableSize` 时的异常行为。

这不能直接证明“我们现在 reparent CAMetalLayer 一定非法”，但结合你的真机日志，我认为这是**非常强的架构信号**：

> MPV Renderer、MetalLayer 和其宿主 UIViewController 最好作为一个完整生命周期单元，而不是把 Layer 从 Renderer 逻辑中抽离，再由 SwiftUI 外层管理。

继续存在。

```text
60fps 原片 + 1×
→ 60fps 视频时间线

60fps 原片 + 2×
→ 120 视频帧/秒时间线

→ 180fps 时间线
→ 屏幕只能显示最多约 120Hz
→ 必须有规律地采样

→ 240fps 时间线
```

这里“规律”两个字非常重要。

我们现在是：

```text

下一帧又来晚了 → 丢
解码器觉得能丢 B 帧 → 再丢
```

所以人物动作节奏是：

```text
显示
显示
丢
丢
显示
丢
显示
显示
丢
...
```

肉眼当然会一顿一顿。

```text
显示
跳
显示
跳
显示
跳
...
```

### 倍速：GitHub 上 MPV 自己其实不推荐我们现在的做法

MPV 官方源码文档对 `framedrop=decoder` 的评价很明确：可能产生非常卡顿甚至画面冻结的结果，decoder dropping 本身很难可靠控制；`decoder+vo` 也明确标记为 **Not recommended**。([GitHub](https://github.com/mpv-player/mpv/blob/master/DOCS/man/options.rst?utm_source=chatgpt.com))

这点在 HEVC + VideoToolbox 上尤其危险。FFmpeg 的 VideoToolbox 代码里，`-17694` 就被明确识别为 `kVTVideoDecoderReferenceMissingErr`。我们之前的真机日志也出现过这个错误。([GitHub](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/videotoolbox.c?utm_source=chatgpt.com)) MPV 自己的 HEVC issue 对 `Could not find ref with POC` 也是按“解码依赖参考帧缺失”来分析的。([GitHub](https://github.com/mpv-player/mpv/issues/3440?utm_source=chatgpt.com))

所以我建议下一版把倍速策略改掉：

- **取消 HEVC/VideoToolbox 的 `decoder+vo / nonref` 丢帧。**
- 恢复 `video-sync=audio + framedrop=vo + vd-lavc-framedrop=none`，先保证 HEVC 参考链完整。
- 2x 以上进入一个独立的 **HighRate Fast Render Profile**，不是破坏解码，而是把渲染负担砍下来：
  - `dscale=bilinear`
  - `cscale=bilinear`
  - `dither=no`
  - `correct-downscaling=no`
  - `linear-downscaling=no`
  - `sigmoid-upscaling=no`
  - `deband=no`
  - 强制关闭运动平滑、超画 shader 等额外处理。
- 回到 ≤2x 后完整恢复用户原来的画质设置。

这其实就是 MPV 自带 `profile=fast` 的思路。官方 `builtin.conf` 的 fast profile 正是把 scaler、dither、linear/sigmoid 等 GPU 开销降到最低。([GitHub](https://github.com/mpv-player/mpv/blob/master/etc/builtin.conf?utm_source=chatgpt.com)) MPV README 也明确建议性能不足导致 stutter 时尝试 `profile=fast`。([GitHub](https://github.com/mpv-player/mpv?utm_source=chatgpt.com))

这里也要说明物理上限：**4K60 × 3x 相当于每秒处理 180 个源视频帧，4x 是 240fps。**iPhone 屏幕只有 120Hz，本来也不可能显示 180/240 个不同画面。我们真正应该追求的是“播放时钟保持 3x/4x、音画同步、显示端稳定取样”，而不是逼 VideoToolbox 通过破坏 HEVC 参考帧来追 180/240fps。这样 3x 仍然会比 1x 少显示部分源帧，但应该是均匀流畅地少，而不是现在这种解码错误式的卡顿。

### 运动平滑：当前方案不是 MEMC

我们目前的：

`video-sync=display-resample + interpolation=yes + tscale=oversample`

确实是 MPV 社区常用的 smooth-motion 配置。([GitHub](https://github.com/mpv-player/mpv/issues/2885?utm_source=chatgpt.com)) 但它是**时间轴采样/混帧**，不是电视那种光流 MEMC，也不是生成真实中间运动帧。MPV 社区自己也有人专门提 issue，指出这套方案和 madVR Smooth Motion 不完全等价，而且 `display-resample` 有额外 CPU/GPU 成本。([GitHub](https://github.com/mpv-player/mpv/issues/7674?utm_source=chatgpt.com))

更关键的是你这台机器是 120Hz，而本次视频是 60fps。**60→120 本身是整数 2:1 cadence**，完全可以一帧显示两个刷新周期，不存在 3:2 pulldown 那种节奏问题。所以这种 60fps 片源默认再开插值，收益非常有限，却白白增加 GPU 压力。你这份日志起播时正好就是 60fps + 120Hz，还开着 `motionSmoothed`。`OnePlayer-Playback-1786957979.log`

下一版我更倾向做成“智能平滑”：

- 60fps→120Hz：**直接帧匹配，不开 interpolation**。
- 30→120、24→120：本身也是整数 4x/5x，优先 cadence duplication。
- 23.976/25 等不能完美匹配时，再根据模式启用 `display-resample`。
- 真正需要柔和混帧时再用 `tscale=oversample / mitchell`，MPV 文档也列出了这些 temporal scaler 的锐度/平滑度区别。([GitHub](https://github.com/mpv-player/mpv/blob/master/DOCS/man/options.rst?utm_source=chatgpt.com))
- **倍速 >1x 时自动关闭运动平滑**，不要让倍速和时间插值同时抢 GPU。

如果以后真想做类似电视 MEMC 的“生成中间帧”，GitHub 上可以走 **RIFE + ncnn Vulkan**。ncnn 官方已经支持 iOS + MoltenVK，并且有 iOS Vulkan arm64 构建。([GitHub](https://github.com/Tencent/ncnn/wiki/FAQ-ncnn-vulkan?utm_source=chatgpt.com)) `rife-ncnn-vulkan` 也是真正的 RIFE 中间帧推理。([GitHub](https://github.com/nihui/rife-ncnn-vulkan?utm_source=chatgpt.com)) 但它现在提供的是“输入两帧→推理一帧”的离线/流水线模型，不是直接能挂进 MPV 的实时 iOS renderer；4K 实时做这个功耗和延迟都很重，所以我不建议现在就塞进正式播放器。

### 超画：GitHub 上有比当前方案更像“超画”的东西

现在 OnePlayer 的“超画”实际上只是 `ewa_lanczossharp + chroma + deband` 这一类 GPU 渲染增强，严格讲它还不是真正的超分。

我们已经用 `gpu-next + Vulkan/MoltenVK`，这条架构最适合先利用 **libplacebo / MPV user shaders**。libplacebo 官方支持 Vulkan，包括 MoltenVK，而且明确支持 RAVU、FSRCNNX、Anime4K 一类自定义 shader。([GitHub](https://github.com/haasn/libplacebo?utm_source=chatgpt.com))

我认为比较值得实验的是 **RAVU-lite**。`mpv-prescalers` 就提供了 RAVU/RAVU-lite 的 mpv user shader，而且明确有更快的 gather/compute 版本。([GitHub](https://github.com/bjin/mpv-prescalers?utm_source=chatgpt.com))

Anime4K 也能直接挂 MPV GLSL，但它更偏动画；官方文档自己提醒：60fps 每帧只有约 **16ms** GPU 时间，而 x2 后再跑 shader，处理量可能达到四倍。([GitHub](https://github.com/bloc97/Anime4K/blob/master/md/GLSL_Instructions_Advanced.md?utm_source=chatgpt.com)) 所以不适合作为所有真人片源的通用“超画”。

我建议最后做成智能分级：

**4K源 → 手机屏幕**本身是在下采样，不应该再做 AI 超分；只开轻量锐化/色度/去色带。**720p/1080p → 高分屏**时才允许 RAVU-lite 之类真正的上采样增强。而且只在 1x 时启用，进入高倍速自动退出，避免跟倍速争 GPU。

### 你说的二级菜单“抽动”，当前实现我也找到原因了

上一版虽然把两个页面都 bottom anchor 了，但当前源码仍然在同时做三件事：

1. 整个弹窗高度从 `139 → 224` 动画；
2. 页面同时做 opacity；
3. 页面同时做横向 offset。

而玻璃背景还是 `UIVisualEffectView`，也跟着 SwiftUI 每帧改变高度。也就是说每次进入二级菜单都是 **SwiftUI 重新 layout + clip + UIKit blur resize + 内容平移/渐变同时发生**。这就是现在仍然感觉“一抽一抽”的根源。当前 main 源码就是这个结构。

下一版我不会再调什么 0.20s、0.28s 曲线了，**结构直接改掉**：父级只留一个固定 258×224 的 overlay 空间，一级卡片和二级卡片各自拥有自己的固定尺寸和毛玻璃，不再共享一个会伸缩的容器。切二级时只做一次水平 push + 很轻的 opacity，一级 139 高的卡片退出、二级 224 高的卡片以最终尺寸进入，全部 bottom anchor。**没有任何内容参与纵向 layout 动画，也不对 UIVisualEffectView 做实时拉伸。**

所以这轮我建议不是继续微调现有参数，而是直接做三项结构性修改：**倍速改成安全解码 + fast-render profile；平滑改成 cadence-aware；超画引入条件式 libplacebo shader 路线；同时重做二级弹窗的页面切换结构。**这几项都不需要提高 Deployment Target，仍然保持 iOS 15.0，iOS 17.0 真机不受影响。

# 这也是 KSPlayer 值得我们研究的原因

KSPlayer 的 `KSMEPlayer` 正好处于两者之间。

它不是 AVPlayer，也不像 MPV 那样套完整跨平台播放器。

官方架构明确是：

```text
FFmpeg
   ↓
KSMEPlayer
   ↓
VideoToolbox 硬解
   ↓
MetalPlayView

Audio
   ↓
AVAudioEngine
```

也就是说，它已经替我们做了一套**Apple 平台定制 FFmpeg 播放器**。([GitHub](https://github.com/kingslay/KSPlayer/blob/main/Documents/KSPlayer%E5%8E%9F%E7%90%86%E8%AF%A6%E8%A7%A3.md?utm_source=chatgpt.com))

它目前公开说明支持：

```text
H264/H265硬解
4K
HDR/HDR10/HDR10+
Dolby Vision
Dolby Atmos
文字/图片字幕
PiP
多音轨
```

最低要求也只是 **iOS 13+**，所以不会破坏我们 iOS 17.0 / 优先 iOS 15 的目标。([GitHub](https://github.com/kingslay/KSPlayer?utm_source=chatgpt.com))

而且一个非常值得注意的信息是，KSPlayer 官方列出的授权版功能里甚至明确写了：

> Smoothly Play 8K or 120 FPS Video

以及：

> Annex-B async hardware decoding

这说明它作者确实专门做过 **Apple 平台高吞吐 VideoToolbox 调度**。([GitHub](https://github.com/HenderRicard/ksplayer?utm_source=chatgpt.com))

这对我们现在正在碰的 **4K60 高倍速**问题非常有参考价值。

但这里不能直接得出：

> KS 一定比 MPV 快。

必须真机测。

因为：

```text
8K/120fps正常播放
```

和：

```text
4K60 × 4x
```

不是完全相同的问题。

而且 KSPlayer 默认 GPL，官方也提供付费 LGPL/其他授权。这个依赖在正式决定采用之前必须把许可证处理清楚。([GitHub](https://github.com/kingslay/KSPlayer?utm_source=chatgpt.com))

# 所以我现在不建议“MPV 一统天下”

我更建议 OnePlayer 最终变成这样：

```text
                  OnePlayer
                     │
        PlaybackPresentationCoordinator
                     │
       UnifiedMediaTransportSession
                     │
             PlayerEngineProtocol
          ┌──────────┼──────────┐
          │          │          │
      AVPlayer      MPV       KSME
       Adapter     Adapter     Adapter
          │          │          │
     AVFoundation  libmpv    FFmpeg
                   FFmpeg       │
                     │      VideoToolbox
                  gpu-next      │
                     │        Metal
                  MoltenVK
```

这里特别重要：

**统一 Transport 和播放器 Engine 是两件事。**

不管最后是什么引擎：

```text
AV
MPV
KS
未来自研
```

媒体都应该继续从：

```text
STRM
 ↓
302
 ↓
115 CDN
 ↓
UnifiedMediaTransport
```

直接拿数据。

**绝对不能因为换 KS 就把 NAS 重新变成媒体代理。**

# 哪个应该是“主引擎”？

按照你现在的媒体环境，我会这样定位：

| 类型 | 默认引擎 |
|---|---|
| MKV / ASS / PGS / 特殊音轨 / 奇怪封装 | **MPV** |
| 普通 MP4 / H264 / HEVC / Apple 友好媒体 | **AVPlayer 可优先** |
| MPV 出现异常 EOF / 解码兼容问题 | **KSME / FFmpeg fallback** |
| 高倍速性能特殊场景 | 后续根据 benchmark 自动选择 |
| Dolby Vision / Apple 原生能力明显占优 | AVPlayer 优先评估 |
| 超画 / shader / 高级画质处理 | MPV 优先 |

所以我仍然赞成：

> **MPV 是 OnePlayer 的主要兼容引擎。**

但是我不赞成：

> **OnePlayer = MPV 前端。**

这两个概念差别非常大。

# 我甚至建议把“主要播放引擎”这个概念逐渐淡化

以后用户看到的可以只是：

```text
播放引擎

○ 自动
○ MPV
○ AVPlayer
○ KS / FFmpeg
```

默认：

**自动**

然后由：

```text
PlaybackEngineSelector
```

判断。

比如这次：

```text
MKV
HEVC
3840×1616
60fps
EAC3
3x/4x
```

Selector 可以知道：

```text
MPV 当前 capability:
4K60 high-rate = poor

KSME benchmark:
4K60 high-rate = good

→ 当前播放临时选择 KSME
```

而普通：

```text
MP4 HEVC Dolby Vision
```

可能：

```text
→ AVPlayer
```

复杂 ASS：

```text
→ MPV
```

这才是真正成熟的播放器架构。

## 我认为现在非常值得做一件事

**先不要马上把 KSPlayer 正式塞进 OnePlayer。**

我们可以专门建立一个：

```text
Player Engine Lab
```

拿**完全相同的 UnifiedMediaTransport 数据源**，分别喂给：

```text
AVPlayer
MPV
KSMEPlayer
```

然后在你的 iPhone 15 Pro Max / iOS 17.0 上固定跑：

- 4K60 HEVC：1× / 2× / 3× / 4×
- 1080p24
- MKV + EAC3
- ASS 字幕
- Seek 连续双击
- STRM → 302 → 115
- 异常短视频
- 后台 → 前台
- 内存 / CPU / GPU / 温度
- A/V drift
- 实际 fps
- 首帧耗时

这样我们就能得到一张真正属于 OnePlayer 的：

```text
Engine Capability Matrix
```

而不是继续凭“MPV 名气大”“KS 看起来快”决定核心架构。

**如果 KSME 在同一个 4K60 文件上 3×/4× 确实明显比 MPV 丝滑，那我会非常赞成让它承担高倍速/异常媒体路径，甚至以后逐步成为主要 FFmpeg 引擎；MPV 则继续承担字幕、shader、复杂格式和超画能力。**

所以当前我的建议是：**MPV 保持主引擎地位，但从现在开始不要再把任何新功能设计成“只有 MPV 才能实现”。下一步应该先对 KS/KSME 做一次真实接入可行性和性能实验。**
