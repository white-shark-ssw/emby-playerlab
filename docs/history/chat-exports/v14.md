最开始以为是异常 MP4 的 **EOF / duration / Range / 302 / 缓存**问题；修完后发现不是。后来怀疑是 **Seek 后 HTTP stream 被截断**；修了 persistent HTTP 后，问题仍存在。再后来发现 MDK Seek 会返回 `-8`、首帧不恢复，于是做 generation recovery；结果进一步发现**同进程创建第二个 MDK Player 反而可能把 renderer/native 生命周期拖死**。最后才发展到现在的 single-generation、native quarantine、独立 watchdog。

而现在最大的瓶颈也已经比较明显了：

**我们已经进入 MDK 黑盒内部。**

UnifiedTransport 能正常提供数据，MPV 能从同一个位置继续播放，说明我们的 302、115、Range、缓存这些上层链路至少不是主要矛盾。真正异常发生以后，是 MDK 自己内部的 demux / seek / decoder / playback state 某一层进入了异常状态。

问题在于 swift-mdk 给我们的主要是 MDK 对外 API。我们可以看到：

> `prepare()`、`seek()`、状态回调、`mediaStatus`、render、buffered……

> FFmpeg demux 到异常 packet → timestamp/index 出问题 → MDK 内部如何处理 → 为什么 seek 返回 -8 → 为什么某些情况下 native 调用不再返回

我们现在**看不到足够深的内部状态，也很难直接修改 MDK 内部决策**。

这就是为什么最近几个版本越来越像“隔离 MDK”，而不是“修复 MDK”。

**“MDK 出问题以后，怎么保证 OnePlayer 不跟着死。”**

**“为什么 MDK 会出问题，以及怎样让 MDK 正常吃掉这个异常文件。”**

2. **MPV 对照**：因为 MPV 已经能够跨过去，所以重点不是证明 MPV 能播，而是看它跨异常点时采取了什么行为，例如是否丢弃损坏 packet、重新寻找关键帧、修正 timestamp、重新打开 demuxer 等。

3. **MDK 直读文件/直链对照**：尽量绕开 OnePlayer 的缓存调度和复杂恢复，只让 MDK 最小化播放同一个媒体。如果此时同一位置仍稳定出错，就可以基本把 UnifiedTransport、UI、播放器控制器排除掉。

4. **OnePlayer 当前 UnifiedTransport + MDK**：和第 3 组比较。如果只有这一组坏，那么问题还在我们应用层；如果第 3、4 组以几乎相同方式坏，而 FFmpeg/MPV 正常，那么范围就已经压到 MDK。

真正决定“应用层还能不能修”的，是接下来这个分界。

### 如果出现这些结果，值得继续修 MDK

假如我们发现改变**输入方式或 MDK 可配置参数**就能改变结果，例如：

- 从异常点 Seek 会死，但提前 1～3 秒从关键帧开始可以跨过去；
- 硬解 VT 会死，FFmpeg 软件解码可以过去；
- 某个 `err_detect / discardcorrupt / genpts` 一类 demux 策略能过去；
- 直接 Seek 到 Resume 点失败，但先从前一个关键帧 prepare，再快速解码到 Resume 点可以过去；
- MDK 拿到的 HTTP Range 与 MPV 实际请求模式明显不同；
- 给 MDK 提供经过应用层修正的媒体字节流后可以正常播放；
- MDK 本身没有死，只是我们错误理解了某个状态、EOF、Seek 返回值。

这些都意味着：

**MDK 内核虽然有弱点，但我们可以从外面改变输入或者调用策略绕过去。**

这种情况下就值得继续攻。

**故障位于 MDK 内部，而且应用层没有足够控制面修复。**

MPV 自动切换只是**安全兜底**，不是我们的解决方案。

这一点非常重要。

---

## 我重新确认后的关键事实

- **MDK 卡死早于自动 MPV 机制。** 最开始没有自动切 MPV 时，MDK 就已经会卡住；后来 Build86/87 左右加入 native isolation / watchdog / quarantine，再自动切 MPV，是为了防止 MDK native worker 把整个 App 一起拖死。也就是说 MPV 不是问题来源。历史记录也明确显示 MDK render worker 可以数秒不返回，然后才被隔离切走。`CharGPT-苹果App开发方案v13.md`
- **异常位置不是“后面视频全坏了”。** Build92/93 多次从 43～59 秒附近重新建立 MDK Player，每次都还能继续推进几秒；MPV 接管后又可以继续播放很远，所以后面的媒体数据明显存在。`CharGPT-苹果App开发方案v13.md`
- **MDK 的 `End` 状态曾经被我们误判得太积极。** 出现过 `0x164` 包含 End，但同一个 MDK Player 后面仍继续从约 20 秒播放到 46 秒，所以 `End bit ≠ 真实 EOF`。这促成了后来的 Confirmed EOF 机制。`CharGPT-苹果App开发方案v13.md`
- **改成 FFmpeg native AVIO 也没有解决。** Build88 已经出现过 Seek 大约 160ms 成功、甚至已经有新画面，然后紧接着 MDK 又进入 premature EOF。`CharGPT-苹果App开发方案v13.md`
- **绕过 localhost、让 MDK Direct HTTP 也没有神奇解决问题。** Build89 直接走 `Emby → 302 → 115/CDN → MDK`，但高速 UnifiedTransport 缓存因此被绕过，实际 Seek 变成约 1.2～1.8 秒、`bufferHit=false`，并且仍发生长时间 Stall。所以 Build89证明了“单纯删掉 localhost”不是完整答案，但因为它同时改变了缓存输入方式，也不能作为严格单变量实验。`CharGPT-苹果App开发方案v13.md`
- **本地 file:// 实验非常有价值，但有一个需要纠正的说法。** 本地文件下 MDK 成功打开同一 MP4，识别 HEVC/AAC，音频正常、播放时钟持续推进、Seek 很快，而且没有出现在线那种 49 秒 premature EOF；但我们自己写的 iOS MDK renderer 没真正把画面显示出来，所以严格说目前证明的是“MDK 核心读取/解封装/音频/时钟/Seek 基本正常”，还不能说本地最终视频呈现已经完全验证。
- **现在最强的证据就是你刚刚强调的“完整缓存仍然卡”。** Build100 日志里，在 MDK 停在 `48.866s` 时，UnifiedTransport 已经明确记录：`cached=1987607878`，正好等于整个文件 `1987607878` 字节，`holes=0`、`slot0=idle`、`slot1=idle`、`refill=false`--也就是整部视频已经完整落在手机里。随后 MDK 仍然确认 End，并在 49 秒触发 premature EOF，然后切 MPV。`OnePlayer-Playback-1787206941.log`
- **因此“115 下载不够快 / 当前字节没下载到”已经不是当前第一嫌疑。** 在 Build100 这次故障瞬间，根本不存在需要等 115 的问题。`OnePlayer-Playback-1787206941.log`

这最后一点，把整个调查范围一下缩小了很多。

# 我们现在实际上有三种输入模式

| 模式 | 数据路径 | 目前结果 |
|---|---|---|
| 本地文件 | `file:// MP4 → MDK` | 解封装、AAC、时钟、Seek 正常；我们自己的画面输出层黑屏 |
| 在线 Unified | `缓存/115 → UnifiedTransport → localhost HTTP → FFmpeg native AVIO → MDK` | 约 40～60 秒区域反复 End/EOS / native stall |
| 在线 Direct HTTP | `Emby → 302 → 115 → FFmpeg HTTP → MDK` | 也不稳定，而且失去 UnifiedTransport 高速缓存优势 |

当前 Build100 用的是第二种。起播日志也明确是：

`MDKIO mode=ffmpeg-native-avio`

以及：

`transport=unified-localhost`

所以这里已经不是我们以前的 Swift custom AVIO。`OnePlayer-Playback-1787206941.log`

```text
UnifiedMap:
cached = 1987607878
total  = 1987607878
holes  = 0
slot0  = idle
slot1  = idle

MDKEndCandidate confirmed

↓

premature EOF at 48.866s

↓

```

`OnePlayer-Playback-1787206941.log`

所以现在可以相当明确地说：

> **49 秒这次故障不是因为 MDK 等不到媒体字节。**

但还有一个非常关键的区别：

即使全部缓存完成，在线 MDK 看到的仍然不是普通文件。

它看到的是：

```text
完整本地缓存
↓
TransportHTTPServer
↓
127.0.0.1 HTTP Range
↓
FFmpeg native AVIO
↓
MP4 demuxer
↓
MDK
```

而真正本地播放是：

```text
完整 MP4 文件
↓
file://
↓
MP4 demuxer
↓
MDK
```

所以“已经完整缓存”和“MDK 直接播放本地文件”**不是一回事**。

# 当前最值得怀疑的层

现在我会把嫌疑顺序重新调整为：

**第一嫌疑：MDK / FFmpeg MP4 demux 在 seekable HTTP 输入下的状态。**

尤其是这个异常 MP4 的：

- sample table / index；
- seek 后 demux position；
- EOF / EOS；
- `MediaStatus.End`；
- FFmpeg HTTP seek；
- Range 边界；
- 非零位置重新 prepare；
- 某个异常 GOP / DTS / PTS 后的 demux 状态。

因为本地 `file://` 和 HTTP seekable 输入，在 FFmpeg 层并不是完全相同的 IO 行为。

**第二嫌疑：OnePlayer localhost HTTP bridge 的语义。**

例如：

- Range 响应结束方式；
- Content-Length / Content-Range；
- 连接关闭还是 keep-alive；
- FFmpeg 小 Seek 如何被转换成 Range；
- 某些短读是否被 FFmpeg解释成 EOF；
- 一个 HTTP request 到范围末尾时是否被错误视为媒体 EOF。

但是它现在不能被单独定罪，因为 Build89 Direct HTTP 也没有让 MDK彻底正常。

**第三嫌疑：MDK 对这个异常 MP4 本身的 demux/native 状态。**

这个仍然不能完全排除。因为我们目前的本地播放器没有真正显示画面，只证明了大量底层行为正常。

但它的优先级已经明显低于最开始。

**115 CDN、总下载速度、是否缓冲够，则应该降到很后面。**

Build100 已经用完整缓存把它大幅排除了。

---

# 还有一条历史经验值得重新利用

其实我们的项目以前已经遇到过非常相似的“**数据明明在本地，播放器消费层还是卡**”问题。

0.9.0 的 AVPlayer 曾经也是：

`UnifiedTransport → localhost HTTP → AVPlayer`

当时缓存和下载速度都很好，但 AVPlayer 的 playable 数据仍掉到 0.1 秒左右并 Stall。后来 0.9.1 把 AVPlayer 改成直接通过 `AVAssetResourceLoader` 消费同一个 ByteStore，去掉 localhost HTTP 中间层，问题方向就发生了明显变化。`EmbyPlayerLab-v0.9.0-to-v0.9.1.patch`

这不能证明 MDK 现在也是 localhost 的锅，但它说明：

> **“ByteStore 数据已经存在”不代表经过 localhost HTTP 包装之后，播放器/demuxer看到的行为就等价于本地文件。**

这和我们当前 MDK 的现象高度相关。

# 所以现在不应该继续做什么

接下来我认为应该停止几类无效循环：

不要继续调：

`Range 16MB → 32MB → 64MB`

也不要继续围绕：

`1 lane → 2 lane`

或者：

`watchdog 4 秒 → 2.5 秒`

这些都不是当前根因。

同样也暂时不要把重点放在：

**MPV 第二次创建卡死。**

MPV 生命周期问题可以以后单独修，但它不是我们当前为什么 MDK 在 49 秒挂掉的答案。

如果：

### B 能穿过 49 秒，继续正常到 60、120、180 秒

那几乎可以直接下结论：

> **视频本身 + MDK decoder 没问题，问题就在 HTTP/AVIO/demux 输入语义。**

之后我们就不用再折腾 MDK decoder。

直接研究：

`HTTP Range → FFmpeg AVIO → MP4 demux`

甚至考虑 MDK 在完整缓存后直接无缝切成本地文件输入。

这可能最终还能变成一个正式优化：

> **视频完整缓存后，MDK 自动从 localhost HTTP consumer 转为本地完整文件 consumer。**

不过这是后话，先证明。

---

如果：

### B 在同一个 49 秒区域也卡

那 localhost、115、Range 基本就可以全部放下了。

应该转向：

- MDK demux；
- FFmpeg MP4 index；
- 异常 DTS/PTS；
- HEVC sample；
- MDK 0.38 对该文件的 bug；
- MDK options / FFmpeg tolerance；
- 必要时比较 CapyPlayer 使用的 MDK 版本和参数。

---

如果：

### B 可以播放，但只有画面 renderer 异常

那我们仍然可以通过：

- MDK position；
- audio；
- packet/frame；
- status；
- End/EOS；
- decoded frame serial

确认它有没有穿过 49 秒，不必等画面层修完再判断输入问题。
