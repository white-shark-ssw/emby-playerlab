### KSME 倍速其实测成功了

不是“UI 显示 4×，实际没到”。

日志明确有：

- 2×：`requested=2.00 actual=1.98`
- 3×：`requested=3.00 actual=3.02`
- 4×：`requested=4.00 actual=4.02`
- 后续 4× 长采样仍然约 `4.00`

而且都是 `hardwareDecode=enabled`。  

这说明 **KSME 的播放器时钟、VideoToolbox 解码和倍速控制本身是有性能的**。这次实验没有白做。

但你肉眼看到的“跳帧”，要分成两个概念。

这个视频本身是 **60fps**，iPhone 15 Pro Max 屏幕最多 **120Hz**：

```text
1× = 60 帧/秒
2× = 120 帧/秒
3× = 180 帧/秒
4× = 240 帧/秒
```

所以 **2×刚好顶到120Hz；3×和4×从数学上就不可能把所有源帧显示出来**。

4×时 1 秒钟内容要求消化 240 张源画面，但屏幕最多刷新120次，至少有一半源帧不能显示。真正需要比较的不是“有没有丢源帧”，而是：

**丢帧是否均匀、帧间隔是否稳定、有没有一顿一顿的 cadence。**

MPV 之前的日志已经出现 3×约 `2.93×`，同时 `voDrops=1932 / decoderDrops=144`，说明它不仅在采样画面，而且解码/输出调度本身也开始吃紧。

KSME 这次至少证明了一件事：

**它维持目标播放速度的能力比当前 MPV 配置漂亮。**

但目前 KSME 没有记录实际 render FPS / dropped frame / frame presentation interval，所以还不能仅凭 `actual=4.02` 证明它比 MPV “更丝滑”。


```text
Seek callback = 25.6ms
```

```text
position=543.215
playable=561.757
loadState=loading
playing=false
```

也就是说 **KSPlayer 的 seek callback 已经告诉我们“成功”，但播放器实际上进入了不播放状态**。

所以现在的 KSME Seek 指标：

```text
25ms
50ms
63ms
```

其实是假的用户体验指标。

它测的是：

**Seek API 接受/完成**

而不是：

**Seek 后第一帧恢复 + 时钟重新前进**

这也是为什么你会觉得“一拉就卡住”。

从当前日志判断，它更像是我们和 KSME 的 `seek → state → resume/play` 生命周期没有完全接对，而不是 UnifiedTransport 或 115 缓存的问题。因为卡住时前面已经有几十秒可播数据，而且明确 `buffering=false`。

所以这个问题理论上**可以修**，但我现在不建议立刻投入很多时间修 KSME。

## MDK 反而很值得测

你说的应该就是 Wang Bin 的 **MDK / Multimedia Development Kit**。

我刚查了它现在的版本。当前 podspec 是 **0.37.0**。它在 Apple 平台直接提供 `mdk.xcframework`，推荐 iOS 使用：

```text
VideoToolbox
+
Metal
+
FFmpeg fallback
```

官方列出的能力包括硬件解码、GPU 0-copy、Metal、HDR、Dolby Vision、ASS/文本/位图字幕，而且特别把 **Continuous Seeking** 当成卖点，官方描述是 Seek 速度可以做到和 mpv 相当，同时 CPU、内存、GPU 开销更低。

这恰好非常对我们胃口，因为 OnePlayer 最重要的并不是“支持多少格式”，而是：

**连续双击 Seek、拖进度、异常文件、4K60、高倍速、115 Range。**

更有意思的是 MDK 最近还在专门继续优化 Seek。0.37.0 changelog 加了 H.264/H.265 decoder frame-drop 来提高 Seek 速度，并增加 HTTP(S) 磁盘缓存。

不过这里也有一个非常重要的现实：

**MDK 也不是“4×不丢帧神器”。**

0.37.0 官方自己就写明：

> playback rate >= 3.0 时，会启用 decoder frame drop 来维持播放速度。

所以在你这个 **4K60 × 4** 场景下，我预期 MDK 的策略跟我们的目标很接近：

```text
宁可有规律地舍弃部分帧
→ 也要保持 4.0× 时钟和 A/V sync
```

关键就变成：

**MDK 丢得是否比 MPV 更均匀、更自然。**

这正是值得真机 A/B 的地方。

---

### MDK 对我们还有两个实际优势

第一是 iOS 兼容没有明显障碍。

当前 CocoaPods podspec 写的是：

```text
iOS deployment_target = 12.0
```

而官方 iOS README 甚至声明 SDK 最低可到 iOS 8。

我们的项目仍然可以保持 **iOS 15.0 Deployment Target**，不需要因为 MDK 提高到 iOS 17。

当然正式采用前，我仍然会按我们的规则直接检查下载下来的 `mdk.xcframework` 每个 Mach-O 的 `LC_BUILD_VERSION`，不能只相信 README。

第二是许可证比公共 KSPlayer 对这个项目更容易处理。

MDK 官方说明：开源项目免费、非商业用户也可以申请免费 key；其他商业使用需要商业 license。没有 key 时新 SDK 可能会在最后一帧显示 QR。

你的这个自用实验项目，**从官方公开政策来看属于值得申请/测试免费 key 的场景**，至少不像公共 KSPlayer GPL 那样一开始就让正式分发架构变得尴尬。

---

## 所以我现在会这样排优先级

**第一：MPV 暂时继续当正式主引擎。**

因为虽然高倍速不够满意，但：

Seek、STRM→302→115、自定义 IO、异常视频、ASS、视频 shader、生命周期这些我们已经踩过大量坑，稳定程度远高于 KSME。

**第二：KSME 留着，不删，但暂停深挖。**

它已经完成自己的历史任务：

> 证明 iPhone 15 Pro Max + VideoToolbox 在这条 4K60 HEVC 上，播放器可以真实维持 3×/4× 时钟。

这个结论非常有价值。

但 P0 的 Seek 现在不过关，而且公共 KSPlayer GPL、和 MPVKit FFmpeg 二进制又不好共存，所以没必要现在把它修成正式引擎。

**第三：我建议下一步做 MDK Engine Lab。**

而且和 KS 一样，不要一开始塞进正式 MPV IPA：

```text
OnePlayer 正式版
└── MPVKit

OnePlayer MDK Lab
└── MDK 0.37.x
├── VideoToolbox
├── Metal
└── MDK/FFmpeg runtime
```

MDK 自己的 iOS framework 内也带 FFmpeg 动态库，官方甚至专门要求给里面的 `libffmpeg*.dylib` 做 code sign。

因此在没有做 Mach-O / 符号 / TrollStore 安装验证以前，我不会假设它可以安全地和 MPVKit 同 Target 共存。

然后仍然用**完全相同的 UnifiedMediaTransport**和今天这个 `174656` 做：

```text
1×
2×
3×
4×

连续 +10 / -10
疯狂连续双击
缓存内 Seek
缓存外 Seek
拖进度 30s → 500s → 100s
后台/前台
异常短视频
```

真正要记录：

```text
actual playback rate
rendered FPS
dropped frames
frame presentation interval/jitter
A/V drift
Seek API latency
Seek → first new frame latency
Seek → playback clock advances latency
CPU / GPU / 内存
```

这样下一轮我们就能真正得到：

**MPV vs KSME vs MDK 三引擎能力矩阵。**

目前如果让我只根据这次真机结果下注，我会是：

**MPV > KSME 作为正式播放器；但 MDK 的试验优先级现在已经高于继续修 KSME。**

特别是 MDK 官方本身就把 **低开销 + 连续 Seek + VideoToolbox/Metal** 当核心方向，它和 OnePlayer 的需求重合度其实比我之前预计的还高。

我认为下一版直接做一个**独立 MDK Lab IPA**，价值很高。

看完了，这次日志其实把 **MDK 的优势** 和 **当前测试包的短板** 都暴露得很清楚。

先说倍速：你的体感不是错觉。这个测试片是 **3840×1616、HEVC Main10、60fps**，MDK 一直走 VideoToolbox。2× 实际大约 `1.92~1.97×`，3× 有 `2.90~2.97×`，后面还能到 `3.04~3.09×`；4× 的多组样本是 **3.86、3.94、3.95、3.97、4.03、4.07×**，平均几乎就是 **3.97×**。其中一段完整 4 秒采样直接是 `requested=4.00 actual=3.97`，另一段是 `actual=4.03`。 

所以至少可以确认一件事：**MDK 在这台 iPhone 15 Pro Max 上跑 4K60 HEVC 的高速播放时钟非常稳，明显比我们之前 MPV 那种高倍速掉速、节奏不均的状态好。** 

不过现在还不能写成“MDK 4× 零掉帧”。60fps × 4 = 240 个源时间帧/秒，而屏幕最高 120Hz，物理上最多只能呈现约一半的不同时间点。真正值得重视的是：**MDK 很可能是在做比较均匀的帧选择/丢帧，所以肉眼没有 MPV 那种不规则的一顿一顿。** 当前日志没有 `renderedFPS / droppedFrames / presentation jitter`，所以只能确认“4×时钟很稳 + 你的肉眼感觉流畅”，还不能证明零源帧丢弃。

反而 5× 已经能看到网络/缓冲开始拖后腿：短样本能到 `4.93×/4.90×`，但持续几秒后会掉到 `4.09×`，甚至另一段到 `3.48×`；同时前向可播长度一度只剩约 **1 秒**。 这说明 **MDK 本身还能继续跑，但当前直接 HTTP 下载已经喂不饱 5×**。

### 高速缓存的问题已经定位

日志里非常直接：

```text
TransportV3 lane=0 session invalidated
TransportV3 lane=1 session invalidated
persistent range pool invalidated
UnifiedTransport stopped
MDKTransport mode=directHTTP302 unifiedTransportStopped=true
```

也就是说目前这个 MDK Lab 我为了先验证“MDK 能不能播放、Metal 能不能出画面、倍速到底怎么样”，实际上让 MDK **自己直接走 Emby → 302 → 115**，启动大约 350ms 后就把我们原来的双 lane `UnifiedTransport` 主动停掉了。

所以你看到的不是“我们的高速缓存变慢了”，而是：

**我们的高速缓存根本没有参与 MDK 的视频字节读取。**

而且目前 MDK 自己的前向缓存也基本被控制在 **约 30 秒**。日志长期都是：

```text
forwardPlayable=29.8
29.9
30.0
```

它不会像我们的 UnifiedTransport 那样双通道持续把 115 带宽跑起来、向前预取几百 MB 甚至 GB。

这也解释了为什么现在 Seek 数据不好看。

例如已经发生的几次：

- 跳到 123.973s：MDK callback **2820ms**
- 跳到 256.620s：**857ms**
- +10s 到 313.150s：**854ms**
- -10s：callback **1081ms**，真正重新推进约 **1779ms**
- 再 +10s：约 **1005ms**

而且每次几乎都会出现：

```text
BUFFERING START
forwardPlayable=0
...
BUFFERING END
```

 

特别有意思的是 +10 秒那次：跳之前 UI 历史上已经显示过 300 多秒附近有缓冲，但 MDK Seek 后依旧重新进入 buffering。说明当前这些 `BufferHistory` **不能当成我们的可复用 ByteStore 缓存**；MDK 原生 HTTP/demux Seek 会重新取数据。

所以现在 **不能据此判断 MDK 的真正 Seek 水平**。我们测到的是：

> MDK Seek + MDK 自带 HTTP/30秒缓存

而不是我们最终想要的：

> **MDK Seek + UnifiedTransport 高速 115 缓存**

### 下一步方向已经很明确

MDK 值得继续做，而且现在优先级已经很高了。下一版 MDK Lab 应该把结构改成：

```text
Emby → 302 → 115 CDN
↓
UnifiedTransport
lane0 + lane1
↓
Unified ByteStore
↓
MDK
```

也就是 **保留 MDK 的解封装、VT 解码、Metal 渲染和它现在很优秀的高速帧调度，只把网络读取换回我们的统一下载器。**

我不会简单把 MDK 自己的 `30s` 调成 `300s/1000s` 来冒充解决，因为那还是两套下载体系。正确做法是 MDK 只保留一个较小的播放器内部 packet buffer，真正几百 MB / GB 的高速缓存继续交给 UnifiedTransport。

接入时我会优先检查 MDK 0.38.0 底层是否能直接提供 **自定义 IO / PacketIO** 给现有 `TransportDataSession`；当前 `swift-mdk` 这一层没有直接暴露我们 KSPlayer 那样的 `AbstractAVIOContext` 接口，所以如果底层 C API 可以接，我会补一个很薄的 Objective-C++/C bridge。只有直接 IO 确实不可用时，才考虑 **iPhone 本机 localhost Range bridge → UnifiedTransport**，依然绝不会让 NAS 中转媒体字节。

另外下一版我建议顺手把 MDK 的测试日志升级，加上 **实际 render callback FPS、帧提交间隔平均值/抖动、每秒提交帧数**。这样再跑 3×/4×，我们就能从数据上判断它为什么肉眼这么顺，而不仅仅依赖感觉。

目前这次测试已经足够让我改变优先级：**MDK 不再只是“再试一个引擎”，它现在是最值得继续打通 UnifiedTransport 的候选。** MPV 的兼容性仍然成熟，但单看你最在意的 3×/4× 流畅度，这次 MDK 的表现明显更有潜力。

### 超画：目前 MPV 更强

如果你说的“超画”包括：

- 高清锐化
- 高质量缩放
- 去色带
- 色彩增强
- AI/Anime4K 类 shader
- 自定义 GPU 后处理

那么**现阶段 MPV 的现成生态明显比 MDK 强**。

所以 MDK 的“超画”路线更可能是：

**MDK 解码 → Metal texture → 我们自己的 Metal 超画 pipeline → 屏幕**

而不是像 MPV 那样直接堆现成 GLSL shader。

这反而未必是坏事。因为我们是自用 iPhone 15 Pro Max，完全可以做几个固定档位，例如：

- 原画
- 轻锐化
- 高质量缩放
- 去色带
- 动漫增强
- 后续再考虑 AI 超分

不需要把 MPV 整个庞大的 shader 配置体系搬进来。

所以我的判断是：

**开箱即用超画：MPV 胜。
如果愿意为 iPhone 专门做 Metal 后处理：MDK 有机会追平甚至超过 MPV。**

### 平滑：MDK 现在反而更有优势

这里要区分两种“平滑”。

第一种是你刚刚看到的：

> **3× / 4× 高倍速仍然感觉连贯、不一顿一顿**

这个 MDK 已经实机明显胜过我们现在的 MPV 配置。

你这个 4K60 HEVC 视频，4× 实际播放时钟仍然基本维持在 4× 附近，而且肉眼看起来均匀。这说明 MDK 的 **高倍速丢帧策略 + 解码调度 + Metal 呈现 cadence** 做得很好。

第二种是：

> 24fps → 60/120fps 的真正“插帧/MEMC”

这个不能因为 MDK 4×很顺，就认为 MDK 自带光流插帧。

目前 MDK 官方公开 feature/API 里，我没有看到明确的 optical-flow MEMC / RIFE 一类插帧能力；不能替它吹这个功能。

MPV 自己倒确实有 `--interpolation`，通过时间轴采样减少刷新率和视频 FPS 不匹配导致的 judder。

但 MPV 的这个也不是电视那种复杂光流补帧。

所以后面我建议我们把“平滑”拆成：

**A. 高倍速平滑**
直接让 MDK 自己做。现在它已经很强。

**B. 普通视频运动补偿平滑**
以后单独研究 Metal / Apple GPU 的插帧方案，不强依赖 MPV 或 MDK。

这样最合理。

## MDK 能不能直接替代 MPV？

我的答案现在是：

### **很可能可以，而且值得认真朝这个方向做。**

MDK 和 MPV 在我们项目里真正重叠的功能非常多：

| 功能 | MDK | MPV |
|---|---|---|
| MKV | ✅ | ✅ |
| HEVC / H264 | ✅ | ✅ |
| VideoToolbox | ✅ | ✅ |
| FFmpeg fallback | ✅ | ✅ |
| ASS 字幕 | ✅ | ✅ |
| Metal/GPU 渲染 | ✅ | ✅ |
| HDR tone mapping | ✅ | ✅ |
| Dolby Vision | ✅ | 部分依赖链 |
| 高倍速 | **目前实机非常好** | 当前表现较差 |
| Seek | 理论很强，待接 UnifiedTransport | 已较成熟 |
| 自定义 shader | 弱一些 | **非常强** |
| 超画生态 | 较弱 | **强** |
| API 集成 | **比较干净** | libmpv 更复杂 |
| 包体/依赖复杂度 | 较低 | 较高 |

MDK 官方甚至直接拿 continuous seeking 和 mpv 比，声称做到“as fast as mpv”但 CPU、内存、GPU 负载更低。这个属于厂商自己的说法，最终还是以我们接上 UnifiedTransport 后的实机数据为准。

所以现在真正决定 MDK 能否取代 MPV 的已经不是“能不能播放”。

只剩几个硬门槛：

1. **UnifiedTransport 接入**
2. Seek 是否能做到我们的 ±10 秒连续双击即时响应
3. 字幕完整性
4. 异常短片 / 坏时间戳 / 提前 EOF
5. HDR/色彩真实设备验证
6. 超画 Metal pipeline
7. MDK license/key 最终解决

这几关全部过，我会支持**把 MPV 从生产播放器里移除**。

而且这样还有一个额外好处：

MPVKit + FFmpeg + MoltenVK 那一堆依赖会少很多，工程和 IPA 都会干净不少。

# 但 MDK 不建议直接替代 AVPlayer

这里要特别区分。

从“播放文件”这个角度：

**MDK 比 AVPlayer 强很多。**

MKV、各种 FFmpeg codec、异常封装、奇怪时间戳、非 Apple 标准媒体，MDK 的覆盖面明显更大。

但 AVPlayer 的价值从来不只是解码器。

AVPlayer / AVKit 是 iOS 的**系统播放器栈**。

例如：

- 原生画中画
- AirPlay
- 后台媒体生命周期
- 系统 Now Playing

### 1. 你说“已经缓冲好的位置，Seek 也会闪一下缓冲速度框”——确实是假的网络缓冲

例如这一次：

- Seek 到 `338.617s`
- MDK 回调只用了 **84ms**
- 日志已经判断 `bufferHit=true`
- 但紧接着 MDK 自己又发出了一次 `BUFFERING START`
- 约几十毫秒后又 `BUFFERING END`

甚至 `MDKSeekHealth` 已经显示播放器时钟开始继续走了，但当时 raw buffering 仍是 true。

326 秒附近也是完全一样：Seek 回调 **103.9ms**，已经是缓存命中，随后 MDK 内部又出现一次很短的 `BUFFERING START → END`。

问题在我们当前适配：

**MDK 的 `MediaStatus.Buffering` ≠ 115 正在重新下载。**

它在 Seek 后需要重新填充 demux/decoder/audio queue，即使所有字节都已经在本机缓存，它也可能短暂进入自己的 buffering 状态。

但现在 OnePlayer UI 是：

`MDK raw buffering → snapshot.isBuffering → 直接显示“正在缓冲 + 115下载速度”`

所以语义错了。

你记得 MPV 当初的情况是对的。之前就专门改过：**transient buffering 不能立刻触发前台缓冲语义，只有持续低前向缓存或真实 Stall 才进入 foreground priority。**

这次 MDK 应该照这个原则处理。

我建议 MDK Seek 增加大约 **500ms 的 buffering UI grace**：

- Seek 本身照样立即执行，绝不 debounce。
- 0～500ms 内 MDK 自己短暂 `BUFFERING`，不显示中央缓冲框。
- 这段时间如果 100～300ms 就恢复播放，用户完全看不到假缓冲。
- 超过约 500ms 仍然没有恢复，而且 UnifiedTransport 确实在等数据，才显示“正在缓冲 + 真实下载速度”。
- 普通播放过程中真正断粮，不受这个 grace 影响。

所以这不是单纯“把框隐藏掉”，而是把**解码器内部 refill**和**网络数据不足**分开。

---

### 2. “缓冲中途停止”这里确实发现了一个真正的 Transport Bug

这部分比 UI 问题更重要。

第二次播放器启动恢复进度时，MDK/FFmpeg 为了解析 MKV，先读了文件头，然后做了一个典型的**文件尾索引探测**：

`start=14521383230 length=1254`

也就是一个 **只有 1254 字节、几乎位于 14.5GB 文件 EOF 的请求**。

结果 UnifiedTransport 把它当成了“播放器真正播放到了文件尾”：

`center reset previous=0 new=14521383230 reason=resume-real-demand`

紧跟着：

`forward full center=14521383230 cached=1254 target=1254 action=stop-preload`

于是后台预取直接认为：

> 我已经缓存到当前播放位置的文件末尾了，前面没有东西需要下载，停止。

但下一瞬 MDK 又正常请求了：

`start=5944 ...`

这才是真实 demux/playback 数据。

所以这个链条已经可以定性：

**MKV 文件尾 metadata probe → 被误判为 concrete playback demand → playback anchor 跳到 EOF → 双 lane 认为 forward window 已满 → 预加载停止。**

这正好解释了你看到的“中途突然不继续缓冲”。

而且在第一次播放的 Seek 中也出现过类似情况：MDK Seek 时先请求文件尾一个约 **34KB** 的 Range，UnifiedTransport 把 center 一把拉到接近 EOF，并取消正在工作的两个 preload lane，然后才出现真正目标位置的 Range。

这和我们以前 MPV/大 MP4 遇到的问题本质上是同一类：

> **demuxer 的 metadata/index/read-ahead 不能拥有 playback anchor 权限。**

之前的设计文档里其实已经明确写过“MP4 尾部 metadata 不改变当前播放需求位置”。

这次漏掉的原因也找到了：UnifiedTransport 现在确实有 `isMetadataProbe()`，但对 `TransportHTTPServer → session.read()` 产生的 **concrete read** 没有继续执行这个保护。MDK localhost 路径恰好把这个漏洞暴露出来了。

---

### 3. 但日志里还有一种 `stop-preload` 是正常的，不能全部当 Bug

当前日志明确显示：

`preloadWindow=2147483648`

也就是当前 Wi-Fi 前向预加载窗口是 **2 GiB**。

因此像下面这种：

`forward full ... cached=2147483648 target=2147483648 action=stop-preload`

本身是正常行为——当前位置前面的 **2GiB 窗口已经全部缓存完毕**，scheduler 暂停下载，等播放中心继续向前移动后再补充窗口。

所以日志中其实存在两种“停止”：

| 情况 | 结论 |
|---|---|
| `cached=2147483648 / target=2147483648` | 正常，2GiB 前向窗口已满 |
| `cached=1254 / target=1254`，center 突然跳到 14.5GB EOF | **Bug，metadata 被误认为播放位置** |

因此 115/CDN 本身这次并没有表现出“下载慢导致停止”。前面很多 32MiB Range 都在快速完成，两条 lane 的持续吞吐整体是健康的。

### 4. 还有一个值得重点追踪的异常 Seek

日志在 `19:19:14.400` 有一次：

`1114.667 → 1124.667`

而当时 `BufferHistory` 已经明确缓存到：

`verifiedEnd=1154.33`

也就是说这个 +10 秒目标肯定在已缓冲区。

`SeekAnchor` 也很快到达了 `1124.667`。

但是接下来日志突然完全断掉，直到 **19:20:16.261** 才出现一个新的播放器会话初始化。

中间大约 62 秒没有：

- MDK Seek callback
- SeekHealth
- Transport 继续下载
- 正常 Lifecycle stop

仅凭日志我不能断言究竟是 MDK 本身卡死、App 被切到后台，还是你重新进入了播放器。

不过这一段非常值得盯，因为目标明确在缓存内。

所以下一版我会建议给每个 MDK Seek 加一个 **2 秒 watchdog**：

如果：

`player.seek()` 已接受
→ 2 秒仍没有 callback / 播放时钟推进

就强制记录：

`position / state / mediaStatus / buffered / UnifiedTransport active lanes / pending Range`

这样再出现一次，我们能直接判断究竟是：

**MDK demux 卡住、decoder 没恢复、local HTTP read 在等、还是 transport scheduler 没响应。**

### 这轮我认为应该先修这 3 件事，再评价 MDK Seek

1. **修 EOF metadata 权限**
- 靠近文件尾；
- 请求非常小，例如 ≤64KB；
- 与当前播放中心相距很远；
- 判为 metadata probe。

它可以最高优先级读取，但：
**不能 reset playback center、不能消费 user-seek token、不能取消双 lane。**

2. **修 MDK 假缓冲 UI**
- Seek 后短暂 MDK internal buffering 不显示中央速度框；
- 约 500ms 后仍未恢复才进入真实 buffering UI；
- 真正未缓存 Seek 仍然会正常显示速度。

3. **增加 MDK Seek watchdog**
- 专门抓你这次 `1124.667s` 这种“缓存明确命中，但之后日志消失”的情况。

另外还有个次要问题：当前 MDK 日志里的 `bufferHit` 是用“Seek callback 是否 <150ms”粗略判断的，这并不可靠。例如真正缓存命中如果用了 167ms 会被写成 miss，115 恰好很快的未命中 Seek 反而可能被写成 hit。这个后面应该改成 **Transport 实际是否发生 blocked read** 来判断，而不是靠毫秒数猜。

所以我现在对 MDK 的评价反而比看到“缓冲框”时更乐观一些：**大量缓存内 Seek 实际已经做到约 80～170ms，真正拖体验的有一部分只是我们把 MDK 内部 refill 错画成了网络缓冲。**

先把这几层污染去掉，再测一次连续 `+10/+10/-10` 和远距离 Seek，那一轮的数据才真正能判断 MDK Seek 值不值得继续深挖。
