### 有一个很重要的区别

我们之前说“选择离目标最近的关键帧”，适用于：

> **低延迟近似 Seek**

```text

后关键帧 600.800
```


因为 H.264 / HEVC 这类帧间压缩视频可以：

```text
关键帧 → 向后解码
```

但不能：

```text
600.800关键帧 → 倒着重建600.000
```

所以精准模式必须找：

> **目标时间之前最近的可随机访问关键帧**

然后向前解码。

```text
      ↓
```


这里 `id=84` 要去 **612.113s**，被我们 fence 丢弃的实际位置却是 **610.217s**。

也就是：

**610.217 - 612.113 = -1.896 秒**

这完全符合 `absolute+keyframes` 的正常“落到目标前一个关键帧”的表现。

而它与 id=83 的 `541.727s` 相差接近 68 秒，所以这个 restart 基本不可能还是 id=83 的旧完成事件。

也就是说：

> **Build136 把 id=84 自己的正确完成事件当成旧事件拦掉了。**

### 为什么会这样

原因已经非常明确。

Build136 当前是在每次 native dispatch 时这样做：

```swift
latestNativeSeekDispatchID = seekID
activeSeekingEpochID = nil
```

然后要求后续再收到一次：

```text
seeking=true
```

才重新：

```swift
activeSeekingEpochID = pending.id
```

问题是 MPV 的 `seeking` 本质上是一个**状态值**，不是“每个 Seek 都必然产生一对 false→true 的 command generation 信号”。

MPV 官方定义也是“播放器当前是否正在 seeking / restart playback”，不是“这是第 N 个 seek 的确认令牌”。([GitHub](https://github.com/mpv-player/mpv/blob/master/DOCS/man/input.rst?utm_source=chatgpt.com))

所以发生了：

```text
id83
seeking false → true

          ↓ MPV 还处于 true

id84 command 发进来了

          ↓

seeking 仍然是 true
```

它不会为了 id84 强制再来一次：

```text
true → false → true
```

于是 Build136：

```text
nativeOwner = 84
seekingOwner = nil
```

但实际上 MPV 已经开始执行 84 了。

等 id84 的正确 restart 到来，就被我们自己拒绝了。
