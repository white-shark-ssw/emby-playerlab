可以，这段新录屏我已经逐帧看过了。**音量 HUD 就按这个竞品的形式做，亮度完全复用同一套视觉和动画，只替换图标并取消震动。**

我看到它的核心不是普通“进度条”，而是一个很明确的**横向刻度尺 HUD**：

```
┌────────────────────┐        │   🔊  38           │        │  │ · │ ·┃· │ · │  │        └────────────────────┘
```

实际效果我准备这样冻结。

**位置与视觉：** HUD 固定出现在画面顶部偏中间的位置，不跟随手指移动；是深色半透明圆角胶囊，面积很小，不影响视频观看。上半部分显示功能图标和整数数值，下半部分是一排短刻度，当前刻度使用明显的亮色竖线，其他刻度使用低亮度灰白色。数值变化时刻度尺连续运动，整体手感就按你这段录屏的形式做，而不是之前说的普通横向 Slider。

**右侧音量：**

```
右侧上下滑↓开始识别为纵向调节↓只出现音量刻度 HUD↓每变化 1%音量立即变化 1%刻度立即移动一格数字立即变化产生一次极轻 Haptic
```

例如：

```
🔊 26🔊 27🔊 28🔊 29
```

步长固定 **1%**，范围 `0...100`。

你说的震动也按这个规则：**每跨过一个 1% 刻度触发一次极短、极轻的触感**，目标就是录屏里那种接近机械滚轮的细密反馈，而不是普通按钮“咚一下”的感觉。我们以大约 **10ms 级瞬态触感**为目标，最终强度和手感在 iPhone 15 Pro Max 真机上调。

这里还有一个重要规则：手指一次快速滑过很多百分比，例如：

```
32 → 40
```

逻辑上就是依次经过：

```
3334353637383940
```

每一格都是独立的 1% 刻度反馈，不把它粗化成 5% 或 10%。

**左侧亮度完全复制：**

```
┌────────────────────┐        │   ☀  38            │        │  │ · │ ·┃· │ · │  │        └────────────────────┘
```

同样：

- 上下滑；
- 1% 步长；
- `0...100`；
- 相同胶囊尺寸；
- 相同刻度尺；
- 相同数字动画；
- 相同出现/消失方式；
- 相同位置。

**唯一差异就是亮度完全没有震动。**

这样用户形成的感觉就是：

```
左边滑☀ 亮度机械刻度无震动右边滑🔊 音量机械刻度有细微刻度震动
```

还有几个从这段录屏里我认为应该一起照搬的细节：

1. **HUD 不唤醒整套播放器控制层。**

控件已经隐藏时调音量，只出现这个刻度胶囊；顶部、底部、播放键都不要跟着出现。
2. **HUD 不跟手指跑。**

它始终固定在顶部区域，这一点比在手指附近显示舒服很多。
3. **松手后短暂保留再淡出。**

不要松手瞬间消失，也不要停留几秒。我建议最终按录屏实际手感做，大约半秒级延迟后快速淡出。
4. **相对调节，不使用手指绝对位置。**

假如当前音量是 63%，用户从右侧任何高度开始向上滑，都是从 63% 开始增加，不会因为起手位置不同突然跳成某个音量。
5. **达到 0% / 100% 后继续滑不会反复震动。**

只有实际跨越一个新的 1% 数值时才触发 Haptic。

所以目前可以把这部分正式冻结为：

| 手势 | HUD | 步长 | Haptic |
| --- | --- | --- | --- |
| 左区上滑/下滑 | ☀ 横向刻度尺 | 1% | 无 |
| 右区上滑/下滑 | 🔊 横向刻度尺 | 1% | 每 1% 极轻一次 |
| 松手 | 短暂保留后淡出 | — | — |
| 控制层隐藏时操作 | 只显示刻度 HUD | — | — |

加上前面已经确定的三分区：

```
左 35%                中 30%                右 35%双击：快退            双击：播放/暂停        双击：快进上下滑：亮度          不处理上下滑           上下滑：音量1% 无震动                                    1% 轻震
```

以及顶部固定的：

```
关闭   标题                  PiP   画面旋转   画面尺寸   ···
```

1. **音量/亮度 HUD 确实做错方向了。** 现在代码本质是“21 根粗刻度 + 一个大黑色 Capsule”，所以才会有你图 1 那种很重、很廉价的胶囊感。

你图 3 竞品的重点其实不是“胶囊”：它几乎没有外框，结构是 **小图标 + 密集细刻度尺 + 百分比**，整体悬浮在黑色画面上，主刻度稍高、次刻度很细，未激活部分只是低亮度灰色。我下一版会把外层大胶囊彻底去掉，改成接近图 3 的轻量横向标尺；音量和亮度共用同一套视觉组件。音量仍保留微触感，亮度仍完全无震动。顺便会把当前 `UISelectionFeedbackGenerator` 的触感再做轻，不要现在这种普通系统 selection 的感觉。
2. **自适应方向和旋转后的画面偏移，是两个相关但不同的问题。** 目前源码其实已经写了“根据视频宽高比自动请求横/竖屏”，而 `Info.plist` 也确实允许 iPhone 横竖屏。

所以你实机完全没有自适应，说明问题不在“没有写这个功能”，而是现在的做法太脆弱：播放器 `onAppear` 后立刻发 `requestGeometryUpdate`，只固定等 **0.12 秒**就开始创建播放器 surface，并没有等系统真正完成方向切换。

你图 2 的状态也说明不能继续靠“请求旋转 + 延时猜系统已经转完”处理。我准备改成：

- 进入播放器后先确定媒体真实显示比例。
- 请求目标方向。
- **监听实际 WindowScene 方向/尺寸完成变化**，而不是睡眠 0.12 秒。
- 实际 geometry 稳定后再启动/重排视频 surface。
- 手动旋转同样走这条路径。
- MPV 的 Metal layer 在每次真实布局变化时重新同步 `bounds / position / drawableSize`，不再只靠当前的条件性修正。
- AVPlayer 也统一跟随最终容器尺寸。

这样要解决的是你图 2 这种“手机已经横屏，但视频层仍拿着旧的竖屏几何尺寸”的问题，而不是简单再加一个延时。

3. **播放记录从头开始这个已经找到明确 bug。** Emby 的 `LibraryItem` 其实已经正确拿到了 `PlaybackPositionTicks`，详情页也能正确显示播放进度。

这次截图和日志对上了，两个问题都能明确判断。

关于第 1 点：**已有播放记录时，不主动回填播放点之前的内容，这是我们之前定下来的正确规则。** `N 向后` 是“已经播放过的数据继续保留 N”，不是从 27:10 续播时主动倒着下载 27:10 以前的 N。你这次日志里真正的播放需求最终从约 `3.77 GB` 建立了新的 Rolling Cache 中心，说明新的 Active Head 已经工作。

不过日志也暴露了一个残留：MPV 启动时先发了 `seek byte=0`，旧逻辑把它误认成了 `resume-real-demand`，所以曾经短暂下载文件头约 16 MiB，然后才迁移到真正的续播字节位置。 这不是“回填播放历史”，而是 **Bootstrap 文件头被错误释放了 Resume gate**。现在已经修成：

```
已有播放记录→ byte 0 / 文件头读取→ 只作为有限 Bootstrap urgent dependency→ Resume gate 继续保持→ 不建立 Rolling Cache center→ 等真正续播位置的真实 byte demand→ 才建立新的 Active Playback Head
```

所以新版会更干净：刚续播时播放点以前原则上不会主动下载；随着正常播放推进，刚刚播放过去的数据才自然成为 `N 向后` 的保留区。

第 2 点这次更关键。日志证明**不是 `VideoLayoutCoordinator` 算错了竖屏尺寸**。你从横屏 Fill 切到竖屏以后，系统已经报告：

```

```

**SwiftUI → VideoLayout → UIView → CAMetalLayer 的逻辑尺寸全部已经转成竖屏，但 MPV/MoltenVK 真正正在使用的 Vulkan 输出/swapchain 没有同步到这个状态。**
